# JWT, caching and Cloudinary photos

JerseySee keeps its existing SQL database for accounts, products, carts, orders,
stock and image metadata. New product image bytes are uploaded to Cloudinary.
Existing SQL and local image files remain readable, so this change does not
require a destructive image migration.

## Render environment variables

Keep the current SQL environment variables and add:

| Variable | Value |
| --- | --- |
| `JWT_SECRET_BASE64` | Base64 encoding of at least 32 random bytes |
| `AUTH_SECURE_COOKIES` | `true` |
| `IMAGE_STORAGE` | `cloudinary` |
| `CLOUDINARY_CLOUD_NAME` | Cloudinary cloud name |
| `CLOUDINARY_API_KEY` | Cloudinary API key |
| `CLOUDINARY_API_SECRET` | Cloudinary API secret |

Generate the JWT key with:
`python -c "import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())"`.
Store all credentials only in Render secrets. Never commit them to Git.

## Image behavior

Administrators and managers continue using the existing product create/edit
form. JPG/JPEG, PNG, WebP and GIF files are validated and limited to 5 MB.
Cloudinary public IDs are generated by the server and cannot be supplied by the
browser. Replaced or deleted Cloudinary images are removed after the SQL
transaction commits. If Cloudinary is temporarily unavailable, the product
database change is not silently treated as a successful image upload.

Existing database and local images continue through the same
`/product-images/{name}` endpoint. Newly uploaded images are streamed from the
configured Cloudinary account through that endpoint, retaining the current
authorization and download behavior.

## Authentication and cache

The browser login issues a 30-minute signed JWT in an HttpOnly, SameSite=Lax,
Secure cookie on production. Forms retain CSRF protection. Account roles,
enabled state and password version are checked on authenticated requests.
`POST /api/auth/login` returns a bearer token for API clients.

Caffeine caches only immutable public featured-product cards for three minutes.
Product, variant, order and stock mutations clear the cache after a successful
transaction. Authentication, carts, checkout, orders and image authorization
lookups are never cached.
